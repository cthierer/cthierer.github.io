# AGENTS.md

Guidance for coding agents working on this personal website.

## Project Intent

This is Chris Thierer's personal profile site. It should support job search, resume presentation, freelance/moonlighting credibility, and a polished but low-maintenance web presence.

The site should stay simple, semantic, accessible, and easy to revisit after long quiet periods. Favor boring, durable choices over clever infrastructure.

## Positioning And Content

- Primary audience priority: hiring managers and engineering leaders first, freelance clients second, recruiters third.
- Position Chris as a software engineering leader.
- Geographic framing should emphasize the Baltimore/DC area.
- Freelance positioning should focus on small web builds.
- Bethesda/game credits are a supporting detail, not the main positioning.
- Selected work should stay more abstract for now because of confidentiality and positioning.
- Direct `mailto:` links are acceptable.
- Resume output should eventually be generated from shared site data rather than maintained as a separate source of truth.
- Structured content is expected to come from Markdown files eventually. Prefer a content model that can support both the website and resume.
- Privacy-first analytics may be added later for basic page metrics and engagement tracking.

## Architecture

- Static site generated by `src/build/build.tsx` using React server rendering.
- CSS is bundled with Lightning CSS from `src/styles/main.css`.
- Pico CSS provides a lightweight base layer; local CSS should own the site's specific visual language.
- Public assets live in `public/` and are copied into `dist/`.
- Generated output in `dist/` should not be treated as source.

Current source organization:

- `src/layouts/` for document/page shells.
- `src/pages/` for page-level content and page-specific CSS.
- `src/components/` for reusable components and matching component CSS.
- `src/components/icons/` for icon wrappers.
- `src/styles/` for global tokens, typography, import wiring, and broad style layers.

## Development Commands

- `npm run dev` starts the rebuild/watch and local static server.
- `npm run build` builds HTML, CSS, and public assets.
- `npm run check` runs typecheck, lint, and formatting checks.
- `npm run format` applies Prettier.

Note: in some sandboxed environments, `tsx` may need approval because it opens an IPC pipe under `/tmp`.

## Design Direction

The visual direction follows the current comp: warm off-white paper, dark ink text, restrained forest green accents, thin warm-gray borders, compact spacing, and quiet professional density.

When adjusting styles:

- Start with design tokens in `src/styles/base.css`.
- Keep colors restrained and cohesive; avoid introducing a large palette.
- Prefer semantic tokens such as `--site-accent`, `--site-border`, and `--site-surface` over one-off hex values.
- Preserve the compact resume/profile feel. This should not become a marketing landing page.
- Keep typography stable and readable across viewport sizes.

## Accessibility And Semantics

Default to semantic HTML before adding styling hooks.

- Use real landmarks: `header`, `main`, `nav`, `section`, `footer`.
- Keep heading order meaningful. The page hero should usually own the `h1`.
- Use lists for real lists, not layout-only grouping.
- Links should have real destinations before launch; avoid shipping placeholder `#` links.
- Decorative icons should be hidden from assistive tech with `aria-hidden` and empty `alt` text when image-based.
- Interactive elements need visible focus states and keyboard-friendly behavior.
- Do not rely on color alone to communicate state or meaning.

## Maintainability Preferences

- Keep dependencies minimal. Add a dependency only when it clearly reduces maintenance or risk.
- Prefer small, obvious components over abstractions that anticipate future complexity.
- Keep component-specific CSS next to the component and import it through `src/styles/components.css`.
- Keep page-specific CSS in `src/pages/` and import it through `src/styles/pages.css`.
- Avoid unrelated refactors while making feature or design changes.
- If content starts duplicating across the site and resume, introduce a small typed data module before duplication spreads.
- If the hand-rolled build becomes painful, consider Vite only when the trade-off is clearly worth it.

## Commits

- Follow Conventional Commits when creating commits, for example `feat: add resume download link` or `fix: improve header focus state`.
- Keep commit scopes small and intentional.
- Do not commit generated `dist/` changes unless the project explicitly starts treating build output as deployable source.

## Quality Bar

Before finishing meaningful changes:

- Run `npm run check`.
- Run `npm run build` when changes affect rendering, CSS, assets, or build behavior.
- Review generated HTML when changing document structure, metadata, navigation, or accessibility-sensitive markup.
- For visual changes, sanity-check desktop and mobile layouts when feasible.

Keep final notes concise: describe what changed, what was verified, and any known follow-up.
